# Repair expense IDs after shared-ledger imports

This documents the historical Lovable Cloud repair. For the existing-project
cutover to `jaellgweggisthweiabv`, follow [the migration guide](existing-supabase.md)
instead; it includes ID generation and ownership setup in one transaction.

Earlier imports spread a source row into the destination payload, including its
`uid`. A TypeScript type assertion did not remove that field. Explicit IDs bypass any destination identity sequence. Inspection of the deployed
Spend Management database also found that `uid` is a plain column with no default
or attached sequence, despite the original migration declaring identity. Both
schema variants need to be handled; a sequence-only reset cannot fix a missing
sequence.

The import now removes `uid` at runtime and stores the source ID only as
`legacy_uid`. PostgreSQL generates each private row's primary key; duplicate
imports are still matched by `(owner_id, legacy_uid)`.

## Existing databases

Deploy the import fix and apply migration
`drizzle/migrations/0005_ensure_expense_identity.sql` to the **private
Lovable Cloud database**, not the legacy shared source. A frontend publish alone
does not establish that the database migration was applied.

Use the normal Drizzle migration runner, which runs migrations in a transaction.
For a manual SQL editor, run the entire migration inside `BEGIN;` and `COMMIT;`.
The repair briefly locks expense writes, creates `GENERATED BY DEFAULT AS IDENTITY`
when no sequence or default exists, preserves existing rows and IDs, and advances
the sequence past existing IDs without rewinding an already-ahead sequence. With
an existing maximum of 1609 and no prior sequence, the next generated ID is 1610.
Explicit IDs remain allowed. An unexpected existing default is reported rather
than overwritten. It is safe to rerun. Run as the database migration owner, not from a
browser client or a public RPC.

The corrected migration 0004 now skips a missing sequence so a fresh migration
run can reach 0005. For databases where 0004 already ran, 0005 remains necessary.
For a manual repair, run 0005 directly, wrapped in `BEGIN;` and `COMMIT;`; no separate
sequence-reset query is needed afterward. This repository change does not itself
apply SQL to the live database.

After applying, sign in and save a new expense to confirm the live database is
repaired. Do not retry many times to advance the sequence manually.

## Regression checks

- `bun test tests/legacy-ledger.test.ts` verifies imports omit the source primary
  key while retaining `legacy_uid` and duplicate protection.
- Against an empty disposable PostgreSQL database, run
  `psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f tests/sql/expense-identity.sql`.
  This reproduces the collision, applies the migration, checks successful inserts
  and preserved existing IDs, and covers repeated repairs, empty ledgers, and the
  observed plain-column schema (including the expected next ID of 1610).
  The test rolls back its table and data.
